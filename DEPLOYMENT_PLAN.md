# Vyogo Frappe AI Suite — Deployment Plan

This document defines a **single, universal multi-tenancy model** for the **Vyogo Frappe AI Suite** and the procedure for deploying it on **Vyogo Cloud**. The same code path must serve a self-hosted single-site bench, a docker-compose dev stack, a shared bench pool, and a whole Vyogo Cloud cluster. Deployment shape is a configuration choice, never a code branch.

> **Status: IMPLEMENTED — Code changes across all three components implemented and verified via unit & integration tests.**
> Multi-tenancy (§4) is active across `frappe-ai-ui`, `frappe-ai-agent`, and `frappe-mcp-server`. Ready for deployment in Profiles A, B, and C.

## 1. Architecture & Tenancy Model

### 1.1 How Frappe picks a tenant
Frappe resolves the site, and with it the database and file storage, from the **`X-Frappe-Site-Name` header first, then the HTTP `Host` header**. A request carrying neither a known site name nor a matching Host gets `404 Site does not exist`, or is routed to `default_site` if `common_site_config.json` defines one. **Routing to `default_site` is a cross-tenant leak, so no multi-site bench that hosts the AI suite may set `default_site`.**

### 1.2 The universal rule
Three facts are true of every deployment, so the design rests on them only:

1. **`frappe_ai` always knows its site.** The background worker runs inside `frappe.local.site`, so it always sends `X-Frappe-Site-Name`. This costs nothing on a single-site bench and is what makes a multi-site bench work.
2. **Downstream services never guess the site.** The agent and the MCP server use the site the caller named, and only that, for the session check and for every call they make on the caller's behalf. If no site is named, they send no site header and Frappe resolves by Host exactly as it does today. That keeps direct MCP clients (desktop tools with a sid or Bearer token) and existing single-site installs working unchanged.
3. **The bench URL for a site is resolved from the service's own config, never from the caller.** The resolver is an ordered lookup, identical in both services:
   1. `site_routes` — an explicit `site → base URL` map (file, hot-reloaded);
   2. `site_url_template` — a URL with a `{site}` placeholder;
   3. `base_url` — the single default.
   A site that is named but matches neither a route nor a template, when either is configured, is **rejected**. A caller must never be able to steer a request to an arbitrary URL.

Everything else in this document is a way of filling in that config.

### 1.3 Deployment profiles

| Profile | Shape | `site_routes` / template | `base_url` | Site header | Typical use |
|---------|-------|--------------------------|------------|-------------|-------------|
| **A** | One site per bench, one agent+MCP pair | none | that bench | sent by `frappe_ai`, optional downstream | self-hosted, compose, dedicated-tenant benches |
| **B** | One agent+MCP pair per shared bench pool | none | that pool | required | small platforms, early Vyogo Cloud rollout |
| **C** | One agent+MCP pair per cluster or region | `site_routes` rendered from the tenant inventory | unset, or a rejecting sentinel | required | Vyogo Cloud at scale |

Vyogo Cloud runs **Profile C** per region (`in-bom`, `us-east`, `eu-central`), with the routes file generated by `vyogo-cloud-gitops` from the site inventory. Profile B remains a supported fallback for a pool that must be isolated. The manifests in §3 show Profile C with Profile B deltas noted inline.

## 2. Multi-Tenancy & Session Security

### 2.1 Risks in the current code (as of 2026-10-13)

| # | Risk | Where | Status |
|---|------|-------|--------|
| 1 | **No site propagation.** All three services talk to Frappe with no site header. On a multi-site bench every call 404s, or, with `default_site`, lands on the wrong tenant. | `frappe-ai-agent/src/ai_agent/middleware/sid.py` (session check), `frappe-ai-agent/src/ai_agent/integrations/frappe_history.py`, `frappe-mcp-server/internal/auth/strategies/oauth2.go` (session check), `frappe-mcp-server/internal/frappe/client.go` (tool calls) | Open, §4.1–4.3 |
| 2 | **One hardcoded bench URL per service.** Neither service can serve more than one bench. | `config.py` `frappe_url`; `config.go` `erpnext.base_url` | Open, §4.2–4.3 (resolver) |
| 3 | **Cross-tenant session cache.** Flat key `"sid:" + sid` is shared across all tenants. | `oauth2.go` `Authenticate` and `validateSessionCookie` | Open, §4.3 |
| 4 | **Revocation gap.** Default session cache TTL is 5 minutes. | `oauth2.go` (`CacheTTL` default) | Config only, §3.1 sets `token_cache.ttl: 30s` |
| 5 | **Plaintext sid in process memory.** Cache keys hold the raw session id. | `oauth2.go` | Open, §4.3 |
| 6 | **API-key fallback escalates every tenant.** With `auth.enabled: false` the MCP server runs no auth middleware, no user reaches the request context, and every outbound call uses the configured API key with CSRF bypass. | `internal/server/server.go`, `client.go` `setCredentials`, `config.go` `validate` | Config only, §3.1 (auth on, no key shipped) |
| 7 | **Process-wide "is frappe_ai installed" flag.** One boolean per agent process decides for every tenant whether chat history is persisted. | `frappe_history.py` `chat_doctypes_exist` | Open, §4.2 |
| 8 | **Open in-cluster endpoints.** Any pod can POST to the agent with a stolen sid; any pod can reach the MCP server. | Kubernetes | Config only, §3.4 NetworkPolicies |

### 2.2 The Multi-Tenant Resolution Contract

1. **Site is named once, at the edge, by Frappe itself.** `frappe_ai` sends `X-Frappe-Site-Name: <frappe.local.site>` on every call to the agent. The agent forwards the same value to the MCP server.
2. **Site and sid are validated together, then bound to the request.** The agent validates the sid against the named site (`/api/method/frappe.auth.get_logged_user` with the site header, sent to the URL the resolver returns for that site). A sid from tenant A presented with tenant B's site name fails with 401. The validated `(site, sid)` pair travels in request context (a contextvar in Python, `context.Context` in Go) and is stamped on **every** outbound Frappe call by both services.
3. **Absent site means legacy Host resolution, nothing more.** When no site is named, the services send no site header and use `base_url`. This path exists for Profile A and for direct MCP clients. It must never be reachable when a site *was* named: a named site either resolves or is rejected.
4. **The bench URL comes from local config only.** Order: `site_routes`, then `site_url_template`, then `base_url`. If routes or a template are configured and the named site matches neither, the request is rejected (`400 unknown site`). Both services read the same routes file and reload it on change, so onboarding a tenant needs no restart.
5. **Every per-user cache is keyed by `(site, hash)`.**
   ```go
   h := sha256.Sum256([]byte(sidCookie.Value))
   cacheKey := fmt.Sprintf("%s:sid:%x", site, h)   // site may be "" on the legacy path
   ```
   The same applies to any map keyed by user id or email: `Administrator` exists on every site.
6. **User credentials only.** The MCP server ships **without** `FRAPPE_API_KEY`/`FRAPPE_API_SECRET`. The only credential on an outbound call is the caller's own sid plus its CSRF token. The Frappe permission engine on the tenant site is the final authority.
7. **Short session cache.** `auth.token_cache.ttl: 30s`, so logout or admin revocation takes effect within 30 seconds.
8. **The in-cluster perimeter is enforced by NetworkPolicy.** Only bench namespaces may reach the agent; only the agent may reach the MCP server.

### 2.3 Data residency (EU sovereign region)
Every chat turn sends the user's message, page context, tool results and history to the configured LLM endpoint. `openrouter.ai` does not guarantee EU processing. Because the agent is deployed per region, `eu-central` gets its own `AI_AGENT_LLM_BASE_URL`/`AI_AGENT_LLM_PROVIDER` pointing at an EU-resident endpoint, or at OpenRouter under a provider-routing policy the DPA covers. **Do not enable the AI suite for `eu-central` tenants until the provider is signed off.**

## 3. Deployment Manifests (Profile C, per region)

### 3.0 Site routes ConfigMap (shared by both services)
Rendered by `vyogo-cloud-gitops` from the tenant inventory; one entry per site. Both services mount it and hot-reload it.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: frappe-site-routes
  namespace: frappeforge-system
data:
  site_routes.yaml: |
    routes:
      tenant-a.vyogo.cloud: http://standard-v16-001.bench-v16.svc.cluster.local:8000
      tenant-b.vyogo.cloud: http://standard-v16-001.bench-v16.svc.cluster.local:8000
      tenant-c.vyogo.cloud: http://standard-v15-003.bench-v15.svc.cluster.local:8000
```

> **Profile B delta:** omit this ConfigMap and its mounts; set `base_url` / `AI_AGENT_FRAPPE_URL` to the pool. Name the agent and MCP resources with the pool suffix.
> **Profile A** is the same as B with a single-site bench, and needs no site-aware config at all.

### 3.1 Deploying `frappe-mcp-server` via MCP Lifecycle Operator

The Kubernetes SIG Apps **MCP Lifecycle Operator** (`mcp.x-k8s.io`, API `v1alpha1`, only `ContainerImage` sources) provides declarative lifecycle management, hardened Deployment defaults, and readiness validation.

#### Step 1: Install the operator (one-time per cluster)
```bash
kubectl apply -f https://github.com/kubernetes-sigs/mcp-lifecycle-operator/releases/latest/download/install.yaml
kubectl get crd mcpservers.mcp.x-k8s.io
# Confirm field placement against the installed CRD before applying Step 3:
kubectl explain mcpserver.spec.runtime.health
kubectl explain mcpserver.spec.config.storage
```

#### Step 2: ConfigMap (auth ON, no API key, site routing)
> **Strict decoding:** the Go MCP server rejects unknown keys at startup (`KnownFields(true)`). Keep only the sections shown. `erpnext.site_routes_file` and `erpnext.site_url_template` are new keys added by §4.3.
> **No Secret is shipped.** With `auth.enabled: true` and `require_auth: true` the server starts without an API key and uses each user's own session.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: frappe-mcp-server-config
  namespace: frappeforge-system
data:
  config.yaml: |
    server:
      host: "0.0.0.0"
      port: 8080
      timeout: "30s"

    erpnext:
      # Profile C: every named site must match a route; the legacy (no-site) path is disabled
      # by pointing base_url at a sentinel that resolves nowhere.
      base_url: "http://no-default-bench.invalid:8000"
      site_routes_file: "/etc/frappe-site-routes/site_routes.yaml"
      # Profile B: delete site_routes_file and set base_url to the pool URL.
      timeout: "30s"
      rate_limit:
        requests_per_second: 10
        burst: 20
      retry:
        max_attempts: 5
        initial_delay: "500ms"
        max_delay: "5s"

    logging:
      level: "info"

    auth:
      enabled: true
      require_auth: true
      oauth2:
        # Validate every sid against Frappe. Without this, any sid is accepted as "anonymous".
        validate_remote: true
        timeout: "5s"
        # Must stay empty: trusted clients may impersonate users via X-MCP-User-* headers.
        trusted_clients: []
      token_cache:
        ttl: "30s"
```

#### Step 3: `MCPServer` Custom Resource
```yaml

  name: frappe-mcp-server

          type: ConfigMap

            name: frappe-mcp-server-config

        source:
          type: ConfigMap

            name: frappe-site-routes

    replicas: 2
    resources:
      requests:
        cpu: "100m"
        memory: "128Mi"
      limits:
        cpu: "500m"
        memory: "256Mi"
    health:                           # lives under runtime, not config
      livenessProbe:
        httpGet:
          path: /health
          port: 8080
        periodSeconds: 30
      readinessProbe:
        httpGet:
          path: /health
          port: 8080
        periodSeconds: 10
    security:
      podSecurityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault

        readOnlyRootFilesystem: true
        runAsNonRoot: true

          drop: ["ALL"]
```

> `/health` on the MCP server does not contact Frappe, and the agent's `/health` skips the LLM probe for non-Ollama providers. Both probes prove only that the process is up. Run the §5 smoke tests after every rollout. The session cache is per replica; with `replicas: 2` a revoked session may survive up to the TTL on each, which the 30 s TTL already bounds.

*(Without the operator, replace the `MCPServer` with a `Deployment` + `ClusterIP Service` on port 8080 carrying the same env, mounts and security settings.)*

### 3.3 Bench Pool & Site Setup (`frappe_ai` via FPM)

#### Step 1: Add `frappe_ai` to the pool allowlist (`FrappeBench`)
`frappe_ai` is published to the Vyogo FPM registry (`ghcr.io/vyogotech/fpm`, package `vyogotech/frappe_ai`) by its own Package workflow: every tag `v<X.Y.Z>` as a release, every push to `main` as a `-git.<date>.<sha>` prerelease snapshot. The package ships its compiled desk bundle and Python dependencies for amd64 and arm64, so the pool needs no build step. In the bench manifest (e.g. `vyogo-cloud-gitops/manifests/pool/10-standard-v16-001.yaml`):
```yaml
spec:
  apps:
    - name: erpnext
      org: frappe
      source: fpm
    - name: frappe_ai
      org: vyogotech
      source: fpm
```

#### Step 2: Confirm the pool has no `default_site`
```bash
kubectl exec -n bench-v16 deploy/standard-v16-001 -- \
  python -c "import json;print(json.load(open('sites/common_site_config.json')).get('default_site'))"
# Must print: None
```

#### Step 3: Inject `site_config.json` on each tenant site
The agent URL is read **only** from `site_config.json` (the Desk settings page re-syncs from it on load and save, so tenant admins cannot redirect sessions). `frappe_ai_agent_url_unsafe_ok` is required because the ClusterIP is an RFC1918 address, which `_validate_agent_url` otherwise rejects. In Profile C every site in the region gets the same URL; in Profile B it is the pool's agent.
```json
{
  "frappe_ai_agent_url": "http://frappe-ai-agent.frappeforge-system.svc.cluster.local:8484",
  "frappe_ai_agent_url_unsafe_ok": 1
}
```

#### Step 4: Add the site to `frappe-site-routes`, then install
Onboarding order matters: the route must exist before the first chat, or the agent rejects the site.
```bash
# 1. gitops: add "<tenant-site>: http://<pool>.<ns>.svc.cluster.local:8000" to site_routes.yaml and sync
# 2. install
bench --site <tenant-site-name> install-app frappe_ai
bench --site <tenant-site-name> migrate
```
Offboarding removes the route first, which makes the site unreachable from the AI services even if a sid survives.

### 3.4 Network Policies (in-cluster perimeter)

The agent trusts the site header because only bench pods can reach it; the MCP server trusts the agent for the same reason. Bench namespaces carry the label `vyogo.cloud/bench-pool: "true"`.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: frappe-ai-agent-ingress
  namespace: frappeforge-system
spec:
  podSelector:
    matchLabels:
      app: frappe-ai-agent
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              vyogo.cloud/bench-pool: "true"
      ports:
        - port: 8484
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: frappe-mcp-server-ingress
  namespace: frappeforge-system
spec:
  podSelector:
    matchLabels:
      # Match the labels the operator stamps on the MCPServer's pods;
      # check with: kubectl get pods -n frappeforge-system --show-labels
      app.kubernetes.io/name: frappe-mcp-server
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frappe-ai-agent
      ports:
        - port: 8080
```

Kubelet probes are not affected by ingress policies on most CNIs; verify on the Vyogo CNI before rollout.

### 4.1 `frappe_ai` (Frappe app): always name the site
The worker runs inside the tenant's site context via `frappe.enqueue`, so `frappe.local.site` is authoritative. In `frappe_ai/api/chat.py`, `_stream_to_agent()`:
```python
with requests.post(
    f"{agent_url}/api/v1/chat",
    json=payload,
    cookies={"sid": sid},
    headers={
        "Content-Type": "application/json",
        "Accept": "text/event-stream",
        "X-Frappe-Site-Name": frappe.local.site,
    },
    timeout=timeout_seconds,
    stream=True,
) as response:
```
Add the same header to the **Test Connection** call in `frappe_ai/api/health.py`.

### 4.2 `frappe-ai-agent`: resolve, validate, propagate
The agent is the trust boundary: it is the only place the sid is checked, so it must check it against the right tenant on the right bench, then make the site impossible to lose downstream.

1. **Settings** (`config.py`): add `frappe_site_routes_file: str = ""` and `frappe_site_url_template: str = ""`. `frappe_url` keeps its default. Validate at startup that the routes file, if named, parses and every URL is absolute `http(s)`.
2. **Resolver** (`integrations/frappe_routes.py`): `resolve(site: str | None) -> str`.
   - `site is None` → `frappe_url` (legacy path).
   - routes file configured → exact match or raise `UnknownSite`.
   - else template configured → `template.format(site=site)`.
   - else → `frappe_url`.
   Watch the routes file (mtime poll every few seconds is enough; ConfigMap updates are atomic symlink swaps) and swap the map without restart. Log the route count on each reload.
3. **Site contextvar** (`middleware/site.py`, modelled on `observability/request_id.py`): set per request from `X-Frappe-Site-Name` (stripped, may be `None`), with `current()` and `frappe_header()` helpers. `frappe_header()` returns `{}` when no site is set.
4. **Session check** (`middleware/sid.py`): `require_sid()` reads the site, resolves it (`UnknownSite` → `400`), and calls `signed_in_user(base_url, sid, site)`, which sends:
   ```python
   headers={
       "Cookie": f"sid={sid}",
       "Accept": "application/json",
       **site.frappe_header(),
       **correlation.frappe_header(),
   }
   ```
   `UserContext` gains `site: str | None` and `frappe_base_url: str`. A sid belonging to another site now fails with `401 Not signed in`.
5. **History client** (`integrations/frappe_history.py`): take the base URL per call from `UserContext`, not from the constructor; `_headers()` adds `site.frappe_header()`; `chat_doctypes_exist` becomes a `dict[str | None, bool]` keyed by site; the CSRF cache key becomes `(site, sid)`.
6. **MCP client** (`integrations/mcp.py`): `build_mcp_client_for_sid()` adds `X-Frappe-Site-Name` when a site is set. Thread `UserContext` through `services/chat.py` wherever `sid` is passed today.
7. **Rate limiter key**: `f"{site or ''}:{sid}"`.
8. **Logs**: add `site=` to turn log lines; never log the sid.

### 4.3 `frappe-mcp-server`: site in context, site on the wire, site in every key
The Frappe client has no access to the inbound request, so the site and the resolved base URL must travel in `context.Context` as the user does.

1. **Config** (`internal/config/config.go`): add `erpnext.site_routes_file` and `erpnext.site_url_template` (env `FRAPPE_SITE_ROUTES_FILE`, `FRAPPE_SITE_URL_TEMPLATE`). `base_url` remains required as the legacy default.
2. **Resolver** (`internal/frappe/routes.go`): same semantics and reload behaviour as §4.2 item 2; `Resolve(site string) (string, error)` with `ErrUnknownSite`.
3. **Context plumbing** (`internal/auth/context.go`): `WithSite(ctx, site, baseURL)` / `SiteFromContext(ctx)` beside `WithUser` / `UserFromContext`.
4. **Middleware** (`internal/auth/middleware.go`): read `X-Frappe-Site-Name`; if non-empty, resolve it (`ErrUnknownSite` → `400`) and put `(site, baseURL)` in the context **before** `Authenticate`, so the session check uses it.
5. **Session validation** (`oauth2.go`): `validateSessionCookie` takes the site and base URL from the context, sends the `get_logged_user` request to that base URL with the site header, and stores `Site` on `types.User`.
6. **Cache keys** (`oauth2.go`): collapse the duplicate lookups in `Authenticate` and `validateSessionCookie` into one:
   ```go
   h := sha256.Sum256([]byte(sidCookie.Value))
   cacheKey := fmt.Sprintf("%s:sid:%x", site, h)
   ```
   Apply `(site, …)` scoping to the CSRF token cache and the per-caller limiter buckets in `client.go`.
7. **Outbound requests** (`client.go`): build the URL from the context's base URL (fall back to the configured `base_url` only when no site is set), and stamp the header beside `setCredentials`:
   ```go
   if site, base := auth.SiteFromContext(ctx); site != "" {
       req.Header.Set("X-Frappe-Site-Name", site)   // Frappe prefers this over Host
   }
   ```
8. **Tests**: extend `sid_cache_test.go` / `sid_session_test.go`: same sid on two sites yields two entries; site A's entry is never returned for site B; the outbound request carries the site header and the routed base URL; an unknown site is rejected before any Frappe call; no site plus no routes behaves exactly as before.

### 4.4 Out of scope for this gate, tracked separately
* Deeper health probes that exercise Frappe connectivity per route.
* Per-tenant LLM quotas and spend attribution (the `site` log field is the hook for this).
